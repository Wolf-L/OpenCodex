# 网页刷新资源缓存修复

## 问题与修复范围

旧规则只识别文件名末尾的 8 位 Vite hash；新版官方 Webview 使用了
`app-shared-737655e1fb23.js` 一类 12 位十六进制摘要。未改写的这些资源因此错误地返回
`Cache-Control: no-store`，普通刷新也会重复下载。

`gateway/runtime/http/static-assets.cjs` 现在同时识别这两种已确认的命名格式：

- 当前版本命名空间下，未改写的 JS、CSS、字体、图片和 WAV 提示音可以复用浏览器长期缓存。
- 响应期实际改写的 JS 仍为 `private, no-cache, must-revalidate`，通过 ETag 再验证；
  主机类型、语言文案或源文件变化仍会失效。
- 旧命名空间、未哈希文件、未支持的摘要格式和显式禁用缓存开关保持原策略。
- HTML、登录、动态配置和会话数据的缓存策略不变；不跳过 WebSocket 就绪握手。

没有增加服务器缓存上限，也没有新增 Service Worker。内容改写规则发生变化时，仍需按既有机制
更新 patched 资源命名空间，不能在旧的不可变 URL 下发布新内容。

## 生效与排查

更新到包含此修复的 OpenCodex 并重启 Gateway 后，第一次打开会填充缓存，之后的普通刷新可复用。
第一轮只做隔离验证；随后已按用户授权替换本机安装版并重启，实际结果见下节。

如果仍慢，可在浏览器 Network 面板观察：

1. 保持 `Disable cache` 未勾选，用普通刷新而不是强制刷新。
2. 未改写的 12 位 hash 资源应显示缓存命中；不同浏览器也可能发送再验证请求。
3. 实际改写的资源仍允许 304；HTML 和动态配置保持不缓存，这是预期行为。
4. 若资源已命中缓存但界面仍晚出现，应继续测量配置响应、JS 执行与官方运行时就绪时间，
   而不是缓存会话数据或删除握手等待。

## 诊断上报接口的慢请求定位

`POST /api/opencodex/runtime-compatibility/reports` 是异步诊断上报，不是首屏必须等待的业务握手。
`accepted:5` 代表本批接受五条报告，既不是五次重试，也不是五秒耗时。

慢请求拆分表明不能把 Network 总耗时全部归给服务器：

| 采样 | 总耗时 | 请求实际发送前 | 发送至响应首字节 |
| --- | ---: | ---: | ---: |
| 取消提示音前的独立 CPU 样本 | 741.7 ms | 739.6 ms | 1.3 ms |
| 取消提示音后的独立 CPU 样本 | 162.6 ms | 159.4 ms | 1.5 ms |

第一条使用复用的 HTTP/1.1 连接，无 DNS/建连或 Service Worker 耗时，主要等待发生在浏览器侧发送
之前。也观察过一次约 170 ms 的发送后等待，尚未证明它由哪一项服务器操作导致。上表不是受控 A/B
提速结论，不把 742→163 ms 当作接口已被优化；本次没有改动诊断上报逻辑。

源码及 CPU 调用栈确认两个具体优化目标：

1. **前端反复生成全量诊断快照。** `modification-browser-host.ts` 的 `publishSnapshot()` 只用微任务
   合并，每次后续事件又执行 `runtime.snapshot()`；报告器对全量点重新构造、脱敏、计算 JSON 签名，
   然后才做差异过滤。80 ms 的网络合并并没有减少此前的快照 CPU 工作。普通刷新前约 9–11 秒曾出现
   22–26 次上报。应优先合并快照生成或只处理脏点，保留最新计数、异常、顺序和 epoch 重放。
2. **后台同步写完整报告。** 兼容服务默认 25 ms 的持久化定时器执行完整快照、JSON 序列化以及同步
   文件操作，重写当前报告和历史报告，并扫描历史目录。它不在 POST 内被直接等待，但和 HTTP/IPC
   共用事件循环，可能造成竞争。应进一步测量，并改为有序异步原子写入/更充分合并，不能直接删掉
   诊断接口或关闭鉴权。

剩余初始化还有官方功能配置和 React/懒加载工作。已纠正一个此前的定位误区：当前 Statsig bootstrap
走 AppHost `httpFetch.fetch`，不走旧的普通 fetch IPC，本地旧处理器不覆盖该路径。看到旧处理器存在
不能推出请求已本地完成；它的实际网络等待尚需单独计时，不能据此伪造功能配置或跳过账号就绪。
