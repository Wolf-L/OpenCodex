# 网页断线后的 RPC 会话恢复：已批准设计

日期：2026-10-13（Asia/Shanghai）。状态：用户已明确选择“继续实现 RPC 恢复”，按配套计划实施。

## 已确认的问题

当前生产提交 `82410aa` 已修复页面唤醒、重复重试延长截止时间以及后台状态显示。850 项检查中 839 通过、11 跳过，五平台构建成功。

实页故障注入仅在独立测试标签页屏蔽了一次 Gateway ping，未发送聊天。旧连接关闭后新连接握手成功，草稿和模型菜单保留，但随后最近列表显示“无聊天”，官方 RPC 报 `no such export ID: 1`。这说明 WebSocket 就绪不足以证明整个应用恢复。模拟不是操作系统断网实验。

源码证据：`ws-hub.cjs` 的 `removeClient` 关闭官方 MessagePort；`markGatewayWsReady` 却用旧浏览器 portId 再次 connect。服务端建立了新的 RPC 对象表，网页仍引用旧表。现有假 relay 测试把任意字符串当请求，不能覆盖这个官方 RPC 身份契约。该行为在本轮改动前已存在。

模型空白尚未独立定位：更新前两次历史往返均正常；侧栏遮挡及根路由警告不能作为模型初始化错误的证据。

## 选择

1. **建议：短暂保留原 RPC 会话并验证连续性。** 网络短暂中断时接回原 MessagePort，而不是拿旧对象引用连接新 RPC。无法证明连续性时明确提示需要重新加载，保留文字副本，不自动重发。
2. 仅增加应用通道失效提示。改动较小，但每次 WS 断开后仍可能需要刷新。
3. 自动重载整个页面。会丢失附件、未持久化面板状态及编辑器格式，不采用。

## 建议方案的具体边界

- 新能力先通过 hello 协商；旧客户端维持旧通道协议。新客户端连接旧 Gateway 时，断线后明确要求重新加载。
- Gateway 以原网页代际及随机恢复标识隔离会话；恢复标识只留在该标签页内存中，与 clientId、原认证上下文绑定。每次升级仍走原认证，不产生新的网络入口或账号权限。
- 已认证网页的全部 app-host ports 作为一个会话保留最多 90 秒；同一时刻只允许一个当前 socket。旧 socket 的迟到 close/error 不能清理恢复后的会话。
- 双方向为已发送帧计单调序号。恢复握手核对接收位置，明确识别帧缺口，不根据 TCP send 成功推断对方收到。不自动重发已经发送过的业务帧。
- 断线期间仅缓冲尚未发送的下行帧，按顺序交付；有帧缺口、Gateway 重启、会话过期、认证上下文改变或队列超限时停止恢复，清理旧会话并显示“应用连接需要重新加载”。不创建一个新 RPC 对象表冒充旧会话。
- 离线会话最多 32 个，总缓冲最多 16 MiB，单会话最多 1 MiB / 256 帧；上限仅约束断线缓冲，不降低正常连接的大帧能力。容量不足结束最旧离线会话并向恢复端明确报告失效。
- 不恢复权限审批、不撤回或重放不确定结果的调用、不改账号和磁盘会话数据。恢复未成功前不能冲刷浏览器积压 RPC。
- 显示区分别表达 Gateway 与应用通道状态。应用通道失效不假报已恢复；不自动刷新、不自动粘贴草稿。重新加载应由用户明确操作，并说明文字副本不包含附件和格式。
- 显式端口关闭立即释放该端口，过期和 Gateway 退出释放会话、缓冲及计时器。连接关闭无法区分页面退出与短暂断网，因此剩余会话最多保留 90 秒。认证在升级和恢复握手时校验，其他认证上下文不能接回原会话；拒绝不匹配的恢复请求不会清理其他页面的会话，原会话仍按期限释放。恢复标识不进入日志、URL 或持久存储。

## 实施位置及验收

预计涉及 `ipc/ws-hub.cjs`、独立的内存会话生命周期模块、浏览器 bridge、草稿连接面板及其现有兼容性机制；不修改官方安装或 vendor 文件。

测试必须使用有状态 RPC 夹具：对象在第一条连接创建，重连后继续调用原引用。覆盖短断线、旧 socket 迟到关闭、双向缺口、容量与 TTL、重复 hello、认证绑定、跨页隔离、Gateway 重启、停止时清理和未确认调用不重发。

实页验收不能只看连接灯：恢复后打开未在本页读取过的历史、展开模型目录，确认正文和输入区可用，未发送草稿仍在；模拟丢帧或 Gateway 重启时显示真实的不可恢复状态。随后完整检查、五平台 CI、备份安装更新、健康与文件校验。

## 限制

本方案仅让可证明连续的短暂断线自动恢复。超过保留窗口、消息缺口或服务进程重启，仍需明确重新加载页面；在不重放业务请求的前提下不承诺无损恢复所有场景。完整重新初始化官方 RPC 与界面状态是另一项工作，不偷偷扩充到本方案。
